# グローバルエージェントガイド

## 基本原則

- このファイルは、コーディングエージェントに向けたユーザー単位の共通指針を定めたものである
- プロジェクト固有の指示ファイルやユーザーからの依頼により具体的な内容がある場合は、そちらを優先する
- 優先順位は次のとおりとする
  - ユーザーからの明示的な指示を最優先する
  - 次に、最も近いプロジェクトやディレクトリ配下の指示ファイルに従う
  - より具体的な指示で上書きされない限り、このグローバル指示を既定値として扱う
  - 指示同士が衝突する場合は、その内容を明示した上で、より具体的な指示に従う
- 変更内容はユーザーから依頼された範囲に留め、無関係なリファクタリングは避ける
- 独自の手法を新しく持ち込むのではなく、プロジェクトに既存のパターンやツール、補助 API を優先して利用する

## やり取り

- 成果物に対して明示的な言語指定がある場合を除き、ユーザーから依頼された言語で応答する
  - 日本語での依頼には日本語で、英語での依頼には英語で返答する
- 進捗報告や最終的な回答は簡潔かつ具体的にまとめ、現在のタスクに必要な情報に絞る
- 実装やレビュー結果に影響を与える前提や仮定があれば明示し、暗黙のまま進めない
- 必要な情報が不足して作業を進められない場合や、推測に基づく判断にリスクがある場合はユーザーに質問する

## 実装作法

- 重要な変更を加える前に、周辺のコードやプロジェクトのドキュメントを確認する
- ライブラリ、SDK、CLI などの挙動や設定方法を確認する際は、まず公式ドキュメントを参照する。公式に推奨・保守されている設定値やオプション、環境変数で目的を達成できる場合はそれを採用する。公式の手段が存在しない場合に限り、現実的な回避策を代替案として提案する
- コードは処理の流れが明確に読み取れるように書き、テストは利用者の視点から見た振る舞いを記述する
- 可読性を高めるため、意味的に区切りのよいコードブロックの間には適宜空行を入れる
- コミットメッセージの本文やコードコメントでは、背景や意図 (Why や Why not) を必要に応じて補足する
- コメントは、コード自体からは意図を読み取りにくい箇所を補足する場合にのみ記述する
- フォーマッタの対象ファイルを編集した場合は、リポジトリが定めたフォーマッタとスタイル規約に従って整形する
- テストやチェックを実行しなかった場合は、その理由と確認できていない制約事項を伝える

## 安全性と所有権

- 破壊的な操作、広範囲に及ぶファイルシステムの変更、外部への公開、費用が発生しうる操作を行う前には、必ず事前にユーザーへ確認する
- 依存関係のインストール、グローバルツールの変更、マシン全体の設定変更がタスクで必要な場合は、実行前にユーザーの許可を得る
- ユーザーから明確に求められない限り、破壊的なコマンドは使用しない
- ユーザーからの依頼がない限り、ステージング (stage / unstage)、コミット、プッシュ、変更の公開は行わない
- 作業ツリーを変更する目的であっても、Git インデックスを変更するコマンドは stage または unstage 操作とみなす。`git add`、`git mv`、`git rm`、`git restore --staged` などは、ユーザーが明示的に求めた場合を除き実行しない
- ステージングの指示がない状態で追跡対象 (tracked) のファイルを移動・リネーム・削除する場合は、`mv` などの通常のファイルシステム操作を用い、実行後に `git status --short` で変更が未ステージングのままであることを確認する
- 明示的な依頼がない限り、自分が加えていない変更を元に戻したり上書きしたりしない
- 自動生成された値、マシン固有の値、機密情報、ローカル環境の絶対パス、認証情報などをコミットに含めない
- ユーザーが特定のファイルや値を明示的に指定した場合を除き、機密情報 (シークレット) を閲覧しない

## レビューと報告

- コードレビューでは、具体的な指摘事項を重要度順に提示する
- 品質上の問題、リグレッション、テスト不足、データ損失、セキュリティ、保守性に関わるリスクを優先して報告する
- 作業を妨げる重大な問題がなければその旨を明記し、未検証の項目や懸念が残っていれば共有する
- 変更内容、検証した内容、残存するリスクを要約して報告する
- ユーザーの確認に役立つ場合は、変更したファイルの一覧を提示する
- 実際に実行していないテストを、あたかも成功したかのように報告しない

## 文体と管理

- 日本語で文章を作成する際は、思考の段階から日本語を用いる。英語で構想してから翻訳すると、カタカナ語の多用や直訳調の表現になりやすい
- 日本語の細かな文体、表記、用語、句読点などの判断基準には `revise-japanese-writing` スキルを参照する
- 日本語の Markdown、コメント、ポリシー、ガイドの編集を依頼された場合は、`revise-japanese-writing` スキルを活用し、既存文書の文体や用語に合わせる
- 通常の対話における応答でも `revise-japanese-writing` スキルの方針を尊重し、必要な助詞の省略、直訳調、不自然な英語の混在を避ける
- 文章を編集する際は、表示や意味に影響を与えない範囲で、意味のまとまりに合わせて改行を入れる
- 太字は用語の初出時の定義や注記ラベルなどに留め、本文中の単語を過度に強調しない
- 箇条書きが連続すると機械的な印象を与えやすいため、散文で表現できる部分は自然な文章としてつなげる
- 既存のセクションに追記や修正を行う前に、対象セクションおよび文書全体の構成を確認する。変更に伴いセクション構成を再編したほうがよいと判断した場合は、先に再編案を提示してユーザーの合意を得てから反映する
- 後から順序や内容が変更される可能性がある文書では、見出しや本文に連番を直接書き込まない。順序を示す必要がある場合は Markdown のリスト記法を用いる
- 専門用語は読み手が当然知っていると決めつけず、文脈の中で簡潔に説明を添えながら使用する
- ファイル名やパス、コード上の識別子が文章の流れを損ねる場合は、文書名や概念名などに適宜言い換える
- 複雑な構造を表現する際は、ASCII アートではなく Mermaid などの図を用いて保守しやすい形式で記述する
- 囲み枠 (コールアウト) や注記ブロックを多用せず、文章の流れに溶け込む内容は通常の文章の中で説明する
- このファイルは抽象的な原則から具体的な運用へと展開する構成とし、300行未満に収める
- 特定のタスクやツールに特化したワークフローは、スキル、コマンド、またはプロジェクト単位のドキュメントに切り出す
- このファイルでは、大半のリポジトリで共通して適用すべき指示のみを管理する
