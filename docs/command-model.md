# コマンドとタスクの設計

## 目的

日常的に使うコマンドを実行方式ごとに整理し、同じ操作を複数の方法で公開しないようにします。

## コマンドの使い分け

### 単独実行コマンド

- 実装は `bin/` に置く
- mise の `symlink-each` で `~/.local/bin` へ同名のまま公開する
- 利用時は mise タスクを経由せず直接実行できる
- ファイル名に `.sh` などの拡張子を付けず、公開名と一致させる
- 実装言語は shebang で示し、将来実装を置き換えても公開名を変えない

たとえば、次のコマンドです。

- `reveal-repository-with-neovim`
- `switch-branch`
- `switch-branch-remote`
- `search-task`

### `mise bootstrap`

- dotfiles を反映し、初回セットアップに必要なタスクを実行する
- `mise.toml` と OS 別設定の宣言に基づいて実行する
- 通常のリンク処理を独自スクリプトで再実装しない

### `mise run`

- 整形、検証、依存関係の更新など、リポジトリの管理に使う
- `mise tasks` で発見できることに価値がある処理を対象にする
- `mise run install` は `mise bootstrap` と同じ処理を呼ぶ

### シェル関数

- 現在のシェルセッションを直接変更する操作だけを残す
- 外部プロセスにするとカレントディレクトリなどの変更が失われる場合に使う

たとえば、次の関数です。

- `reveal-repository`
- `reveal-repository-with-zoxide`
- `search-theme`

## 設計原則

### 単独実行コマンド

- 日常利用する CLI は単独実行コマンドを優先する
- PATH と mise タスクの両方へ同じ操作を公開しない
- `bin/` の隣接ファイルを利用者が追加しても、`symlink-each` の適用で削除しない
- ShellCheck と shfmt は拡張子ではなく `bin/*` も対象にする
- `.sh` は `libexec/` や `setup/` に置く内部実装で使い、公開コマンドには付けない

### `fzf` の利用

- `bin/` または `setup/` で `fzf` を使う場合は、原則として `libexec/fzf.sh` を経由する
- `--preview` の有無にかかわらず、素の `fzf` を直接呼ばない
- 候補生成、`--bind`、`--delimiter` など、そのコマンドだけで使う処理は呼び出し側に残す
- preview を別シェルで動かす場合だけ、ラッパーの上書き手段を明示する

### mise

- セットアップ、整形、検証、アップグレードの入口に使う
- 短い直接操作をすべて `mise run` で包まない
- 環境と配備の宣言は `mise.toml`、タスク定義は `.mise/tasks/` に置く
- 短いタスクと実行関係は目的別の TOML ファイル、複数行のシェル処理は file task に置く
- dotfiles の状態確認、反映、解除には `mise bootstrap dotfiles` の標準操作を使う

### シェル関数

- カレントディレクトリ変更など、親シェルを変える必要がある操作だけを残す
- 単にツールを起動するだけのものは単独実行コマンドに寄せる

## コマンドの公開

`bin/` に実行可能なファイルを追加すると、次回の `mise bootstrap dotfiles apply` で `~/.local/bin` にリンクされます。`symlink-each` が作成したリンクは mise の状態ディレクトリに記録されるため、配備元から削除したコマンドのリンクは次回の適用で削除されます。`[dotfiles]` の宣言自体を削除する場合は、先に `mise bootstrap dotfiles unapply` の対象を確認します。

公開コマンドから別の公開コマンドを呼ぶ場合も、拡張子なしの公開名を使います。ラッパーを変更したときは、参照先が `bin/` に存在することを検査します。

## 変更時の判断基準

- 新しい CLI を追加する
  - まず単独実行コマンドで成立するかを考える
- mise タスクを追加する
  - リポジトリ運用や一覧性に価値があるかを見る
- シェル関数を追加する
  - 親シェルを変える必要があるかを確認する
