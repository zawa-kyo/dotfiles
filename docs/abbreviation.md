# 省略入力の命名ポリシー

## 目的

シェルの省略コマンドと Neovim の追加キーバインドに共通する命名規則を定めます。シェルとエディタという異なる環境であっても、操作の種類 (動詞) と対象 (目的語) を共通の語順で直感的に把握できるように設計します。

各環境固有の制約や具体的なキーバインド一覧は、実装に近い以下のドキュメントで定義します。

- [Neovim キーバインド設計](../dotfiles/editors/nvim/docs/keybinds.md)
- [Neovim のタブとバッファの表示方針](../dotfiles/editors/nvim/docs/tab-buffer.md)

## 共通文法

- `verb + object` を基本形とする
- 必要に応じて短い修飾子 (qualifier) を付与する
- 実装ツールやプラグイン名ではなく、ユーザーが行う操作に基づいて命名する
- 利用頻度が高い操作ほど短いキー入力を割り当てる
- 各環境の標準操作やキーバインドと衝突する場合は、標準操作を優先する

`verb` は操作の種類を表し、後続するキーの名前空間 (コンテキスト) となります。`object` や `qualifier` の意味は単独の文字だけで決めるのではなく、先行する `verb` との組み合わせで解釈します。同一環境の同一名前空間内では、同じ文字に一貫した意味を割り当てます。

たとえば `sl` は、`s` (search) と `l` (line) の組み合わせによる「行の検索」です。一方で `rl` や `tl` における `l` は、Neovim の location list を表します。すべての操作を横断して 1 文字の意味を完全に固定してしまうと、Vim の標準操作や既存の自然な組み合わせと衝突が生じるためです。

## 共通する動詞

- `g`: go。現在のカーソル位置や文脈から対象へ移動する
- `s`: search。現在の文脈に依存しない検索画面や一覧 UI を開く
- `r`: reveal。対象や現在の文脈に関する情報を表示する

同一の操作をシェルと Neovim の双方で提供できる場合は、Neovim のキーバインド設計を基準に文字を選定します。ただし、各環境の一般的な慣習や標準キーバインドを崩してまで無理に表記を揃えることはしません。

小文字と大文字のペアが存在する場合は、小文字に狭い範囲 (ローカル)、大文字に広い範囲 (グローバル) を割り当てます。たとえば Neovim では、`sl` が現在のバッファ内検索、`sL` がワークスペース全体の検索となります。大文字側に対応する自然な操作が存在しない環境では、対となる入力を無理に追加しません。

## シェルの省略コマンド

シェル環境では、共通の動詞に加えて次の動詞を使用します。

- `a`: add / create / append
- `c`: checkout / change
- `d`: delete / remove

対象と修飾子は、同じ動詞から始まる省略コマンドの中で意味を一貫させます。

- `rr`: reveal repository
- `rrb`: reveal repository with browser
- `rrn`: reveal repository with Neovim
- `aw`: add worktree
- `awr`: add worktree from remote branch
- `cb`: change branch
- `cbr`: change to remote branch
- `sf`: search files
- `sfa`: search all files
- `sfs`: search files case-sensitively
- `sl`: search lines
- `sln`: search lines with Neovim
- `sls`: search lines case-sensitively

省略コマンドの展開先には、`mise run ...` のような中間タスクではなく、利用者が実際に実行するコマンドを直接指定します。

## 例外

`ls`、`vim`、`grep` など、既存コマンドの互換性維持や置き換えを目的とした短縮は、本ルールの対象外とします。既存ツールのエイリアスと、独自に体系化した操作コマンドは明確に区別します。

新しい省略入力を追加する際は、次の点を確認します。

- 同じ動詞の名前空間内で、すでに別の意味が割り当てられていないか
- 既存の短いコマンドや標準キーと衝突しないか
- 入力を短縮する価値があるほど利用頻度が高いか
- 内部の実装やツールを変更しても、操作名として破綻せずに維持できるか
