# リファクタリング計画

## 位置づけ

この文書は、dotfiles の配備処理とディレクトリ構成を段階的に見直すための計画です。
現行仕様は [architecture.md](architecture.md) と [command-model.md](command-model.md) を基準とし、この文書に記載した将来像は、各 TODO の実装と検証が完了した時点で現行文書へ反映します。

この計画は採用済みで、現在は段階的に実施しています。
個々の実装方法は、TODO に記載した事前調査と各段階の検証を終えてから確定します。

## 背景

現在のリポジトリは、設定、パッケージ宣言、公開コマンド、保守タスク、共通処理を分けて管理しています。
`mise run install` をセットアップの入口にし、既存の通常ファイルを上書きしない独自の配備処理も備えています。
Neovim では、プラグイン定義、共通設定、キーマップ、局所ポリシーを分離しています。
これらの責務分割と安全策は今後も維持します。

当初の構成にあった次の問題は、ここまでの変更で解消しました。

- Bun と apm の依存関係の実体が、追跡する設定や lock ファイルと同じディレクトリに生成される
- `bin/` のコマンドを PATH とグローバル `mise` タスクの両方へ公開している
- リンク一覧、リンクの適用、張り直し、旧構成の掃除が複数のシェルスクリプトに分かれている
- ホームディレクトリを書き換える処理に、振る舞いを確認する自動テストがない
- `config/` の用途別分類と実際の配備先を、別々に管理する必要がある

一方、mise が dotfiles とマシンセットアップを宣言的に扱えるようになったため、同等の状態管理を独自の Bash でも維持する必要性は低くなりました。
次の段階では、生成状態の分離を保ちながら、設定を管理対象ごとにまとめ直し、配備とセットアップの標準入口を `mise bootstrap` へ移します。
また、配備、移行、Bun、コマンド公開を 1 つの Bash テストから確認しているため、テストの意図と失敗原因を読み取りにくい点も見直します。

## 目標

### 追跡する宣言と生成状態を分離する

リポジトリには設定、パッケージ宣言、lock ファイルを置きます。
ダウンロードした依存関係、キャッシュ、展開結果などの生成状態は、各ツールが対応する標準ディレクトリまたはリポジトリ外の専用ディレクトリへ置きます。

ただし、単に生成先を変更するためだけに、ツールが想定しない独自配置を導入してはいけません。
Bun と apm が公式に提供する設定や実行方法を確認し、保守されている方法を優先します。

### 配備処理を 1 つのモデルに集約する

配備元、配備先、対象 OS を 1 つの一覧で管理します。
配備処理は、少なくとも次の操作を提供します。

- `apply`
  - 必要なリンクを作成し、管理対象のリンクを期待する状態へ合わせる
- `check`
  - ファイルを変更せず、未配備、リンク切れ、競合を報告する
- `diff`
  - 実行時に変更する対象を事前に表示する

`apply` は何度実行しても結果が変わらないようにします。
現在の `relink` は独立した処理として残さず、`apply` の動作へ統合します。

初回の統合では、追加のパーサーを必要としない Bash の関数呼び出しで配備一覧を記述しました。
次の段階では、同じ状態を mise の `[dotfiles]` に宣言し、状態判定とリンク操作を mise に委ねます。
独自処理は、旧構成からのデータ移行など、mise の宣言だけでは表せない一時的な処理に限定します。

### コマンドの実行経路を分ける

実行経路は次のように分けます。

- 日常的に使う CLI コマンド
  - `bin/` から PATH へ公開する
- リポジトリの保守タスク
  - `mise bootstrap`、`mise run check`、`mise run format`、`mise run upgrade` などに限定する
- 親シェルの状態を変える操作
  - Zsh のシェル関数として管理する

同じコマンドを PATH とグローバル `mise` タスクへ二重に公開しないことを原則とします。
ただし、既存の `mise run <global-command>` の利用状況と `search-task` への影響を確認してから移行します。
必要であれば互換期間を設け、廃止する実行経路を明示します。

### 管理対象ごとに設定をまとめる

配備先をリポジトリ内の配置へそのまま写すと、リンク先は分かりやすくなります。
一方、同じツールの設定とパッケージ宣言が `home/`、`macos/`、`packages/` に分かれ、日常的な変更では複数の最上位ディレクトリを探す必要があります。

mise の `[dotfiles]` が配備元と配備先の対応を一元管理する場合、リポジトリ内の配置に配備先を重ねて表現する必要性は下がります。
次の段階では、設定を管理対象ごとに `config/` へまとめ、配備先と OS の違いは mise の宣言で表します。

```text
dotfiles/
├── config/
│   ├── ai/
│   ├── editors/
│   ├── shell/
│   ├── terminal-apps/
│   └── tools/
├── bin/
├── libexec/
├── tasks/
├── deploy/
│   ├── links.sh
│   └── migrations/
├── tests/
├── docs/
├── AGENTS.md
├── README.md
└── mise.toml
```

`config/` の下では、エディタ、シェル、端末アプリ、ツール、AI ツールという変更理由の近い単位で設定を分けます。
Bun と apm の宣言も各設定の近くに置きますが、`node_modules/` と `apm_modules/` はリポジトリ外へ生成します。
`bin/`、`tasks/`、`libexec/` は、公開コマンド、保守タスク、共通処理という実行時の責務が異なるため、現在の分離を維持します。

## 移行原則

変更は TODO のまとまりごとに分け、振る舞いの変更とパスの変更を同じ段階で行いません。
新しい経路を確認するまでは現在の経路を削除せず、各段階で切り戻す対象と手順を記録します。

移行処理が削除してよいのは、このリポジトリが作成したと確認できるシンボリックリンクと生成物だけです。
通常ファイルと実ディレクトリは暗黙に上書きしません。
既存のシンボリックリンクは mise の標準仕様に従って宣言した参照先へ収束させ、以前の独自判定との完全な互換性は持たせません。

## 維持する設計

次の設計は、配備方法を変更しても維持します。

- `mise` をセットアップと保守タスクの入口にする
- 既存の通常ファイルを暗黙に上書きしない
- 日常コマンド、リポジトリ内処理、共通処理の責務を分ける
- Neovim の `lua/config/`、`lua/plugins/`、`lua/policies/` の役割を分ける
- AI スキル本体を外部の apm パッケージで管理する
- README、設計文書、局所ポリシー、エージェント向け案内を使い分ける

Neovim のファイル数を減らすためだけの統合や、`mise` を別のタスクランナーへ置き換える変更は行いません。

## 次段階の設計

### 標準機能と独自処理の境界

mise は、宣言した状態の判定、変更前の確認、リンクの適用、mise 管理ツールの導入順序を担当します。
リポジトリ側で同じ所有判定や差分表示を再実装しません。

リポジトリには、次の責務だけを残します。

- `mise.toml` と OS 別の mise 設定
  - 配備するファイル、ツール、セットアップ順序を宣言する
- `tasks/`
  - Bun や apm など、宣言だけでは完結しない反復可能な処理を実行する
- `deploy/migrations/`
  - 旧構成にしか存在しない状態を新しい配置へ移す
- `tests/`
  - mise とリポジトリ固有処理を実際に接続し、利用者から見える結果を確認する

`mise bootstrap` を標準のセットアップ入口にします。
`mise run install` は移行期間だけ互換入口として残し、内部から `mise bootstrap` を呼び出します。
移行完了後は、互換入口と独自の `apply`、`check`、`diff` を削除します。

### 配備宣言

`config/` は管理対象ごとの構造とし、`[dotfiles]` に配備元と配備先を明記します。
ディレクトリ全体を同じ単位で管理できる Neovim などはディレクトリ単位でリンクし、他の設定と共有する配備先にはファイル単位の宣言を使います。
macOS 固有の配備先は OS 別の mise 設定へ分け、設定ファイル自体は対象ツールのディレクトリに置きます。

Bun、Homebrew、mise などの宣言は `config/tools/`、apm の宣言は `config/ai/` に置きます。
設定と lock ファイルを同じ管理対象の近くに置きつつ、生成状態はリポジトリ外へ分離します。

現在の `bin/*.sh` は、公開時に拡張子を外した名前を使っています。
`symlink-each` では名前を変換しないため、公開コマンドを拡張子のないファイル名へ変更してから mise に移します。
この変更では、実行権限、説明コメント、ShellCheck とフォーマッタの対象が維持されることを確認します。

配備元を削除した場合の掃除には、mise が記録した所有情報を使います。
設定から項目を消す前に、管理対象だけが削除されることを確認し、必要なら先に `mise bootstrap dotfiles unapply` を実行します。

既存のシンボリックリンクは mise の標準仕様に従って再設定します。
現在の独自処理と同じ所有判定を再現するための前処理やラッパーは追加しません。
既存の通常ファイルと実ディレクトリは暗黙に上書きせず、必要な場合は内容を確認して利用者が明示的に移行します。

### セットアップの順序

宣言的な配備とツール導入が終わった後に、`bootstrap` タスクからリポジトリ固有の処理を実行します。
各処理は単独でも実行でき、途中まで適用された状態から再実行しても同じ状態へ収束するようにします。

`bootstrap` タスクには、実行順を制御するためだけの薄い呼び出しを置きます。
リンクの所有判定、パスの正規化、差分表示など、mise が持つ処理を補助関数として作り直しません。

### テストの境界

配備テストは、一時的な `HOME` と `MISE_STATE_DIR` を用意し、実際の `mise bootstrap dotfiles` を外部入口として実行する結合テストにします。
mise の内部ロジックはテストし直さず、このリポジトリの宣言と mise が正しく接続されることを確認します。

自動テストで確認する振る舞いは次のとおりです。

- 宣言したファイルとコマンドが期待する配備先へリンクされる
- 既存の通常ファイルと実ディレクトリを暗黙に上書きしない
- 既存のシンボリックリンクが mise の仕様どおり宣言した参照先へ収束する
- 2 回目の適用ではファイルシステムの状態が変わらない
- 削除した配備元について、このリポジトリが管理していたリンクだけを掃除できる
- 共通の配備宣言と macOS 固有の配備宣言が混ざらない
- APM、Bun、旧コマンド公開の移行がユーザーデータを失わない

Homebrew、実際のパッケージ取得、実際のホームディレクトリへの適用は、この結合テストに含めません。
外部状態を変更する確認は、dry-run、状態確認、実機での段階的な適用に分けます。

### テスト実装の言語

テストコードは、本番処理と同じ言語であることよりも、シナリオ、準備、操作、観測結果を追いやすいことを優先します。
現在の Bash テストをそのまま拡張することは前提にしません。

候補は次の基準で比較します。

| 候補       | 利点                                                                                 | 注意点                                                           |
| ---------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| Go         | 標準の `testing`、一時ディレクトリ、子プロセスを使い、依存関係を増やさず構造化できる | テストのためだけにプロダクション用の抽象や CLI を作らない        |
| TypeScript | 既存の Bun を使って短く記述でき、ファイルシステムと子プロセスの API も扱いやすい     | 実行環境とテスト用パッケージへの依存を増やさないようにする       |
| Bash       | 初回セットアップ時の追加依存がなく、既存テストと短い移行処理をそのまま実行できる     | アサーション、テストデータ、後始末が増えるとシナリオを追いにくい |

第一候補は Go とします。
標準ライブラリだけで代表的な配備、競合、移行の各シナリオを試作し、既存の Bash テストより意図と失敗原因が明確になる場合に置き換えます。
Go は検証時だけ使い、`mise bootstrap` 自体の実行条件にはしません。
Go を採用する場合は、検証環境を再現できるようにリポジトリの mise 設定へバージョンを宣言します。
この宣言はテスト実行時にだけ参照し、dotfiles の配備前に Go のインストールを要求しません。
Go ではテストの記述量や補助コードが過大になる場合に限り、TypeScript と Bun の組み合わせを試します。
移行スクリプト自体は短命な処理なので、別言語へ移すことを目的にせず、削除しやすい Bash のまま保ちます。

## 検証方針

各段階では、変更対象に応じて [operations.md](operations.md) の手順で確認します。
配備処理を変更する段階では、通常のフォーマットと pre-commit に加え、一時的な `HOME` を使うテストを必須にします。

mise への切り替え中は、独自処理と mise の両方を同じ配備先へ続けて適用しません。
各段階で状態確認と dry-run を先に実行し、適用する処理を 1 つに限定します。

実機でしか確認できない項目は、自動テストで確認できる範囲と分けて記録します。
特に Homebrew、Bun、apm、Neovim の更新処理は外部状態を変更するため、通常の配備テストから分離します。

## 決定事項

- 正式な対応対象は macOS とする
- 共通リンクの一覧は Linux でも検証し、OS 固有の項目が混ざらないようにする
- 設定は管理対象ごとに `config/` へまとめ、配備先と OS の違いは mise の宣言で表す
- 公開コマンド、保守タスク、共通処理は `bin/`、`tasks/`、`libexec/` に分け、生成状態はリポジトリ外に置く
- 既存の通常ファイルを暗黙に上書きしないことを確認したうえで、配備とセットアップの標準入口を `mise bootstrap` へ移す
- シンボリックリンクは mise の標準仕様へ合わせ、以前の独自所有判定を再実装しない
- mise が提供する状態判定、所有管理、差分表示を独自処理で再実装しない
- テスト実装の第一候補は Go、代替候補は TypeScript とし、代表シナリオの比較後に採否を確定する
- 後方互換性は既存データの移行と一時的な `mise run install` の入口に限定し、旧配備処理の挙動を完全には再現しない
- 旧構成の移行処理と互換入口は定常処理から分離し、削除条件を持たせる

初回の配備統合では、追加のパーサーが不要で単独起動できることを理由に Bash を採用しました。
mise の標準機能へ移す段階では、独自実装の少なさ、生成状態の分離、安全な移行、テストの診断性を判断基準にします。
